## Section 4 — Root Causes of the Audit-After-Audit Pattern

### 4.1 Validation pattern was insufficient
Phase 2 validator only checked qualified-decision match (97.9%) — never compared the blocked_reason distribution. A backtest can have 97.9% match on QUALIFIED scans while missing entire gates (because all those gates' would-be rejections still show up as "blocked" in BQ regardless of WHICH gate caught them).

### 4.2 Universe of strategies was scoped to SWING only
- Built backtest for `SWING_SETUPS` (4 setups) without testing whether that captures actual production behavior
- Live data shows production is 61% INTRADAY (VWAP_TREND alone)
- Our backtest can never produce numbers matching live because it tests a different population of trades

### 4.3 Code-vs-Prod deploy verification was never done
- No record of which Cloud Run revision is actually running
- Code comments claim deploys happened (Batch H, 2026-05-06 BREAKOUT park) but live behavior contradicts
- Without verifying what's deployed, every audit of the code is auditing a fiction

### 4.4 Confirmation-bias loop
- Each phase reported a finding, then a new gap was found that invalidated the finding
- I kept moving forward (build new backtest based on new finding) instead of pausing to verify
- User correctly identified this pattern and called for a stop

## Section 6 — What We Should Do Next

### Option A: Honest pause and investigate
1. **Verify what code is deployed** (Cloud Run revision diff vs worktree)
2. **Stop running new backtests** until we can pass equivalence test on ALL blocked_reasons (not just qualified count)
3. **Investigate live -₹673 loss** with the actual deployed code, not the worktree

### Option B: Pivot focus to live diagnostics
The live system has run for ~1 month with detailed blocked_reason logging.
That data is more trustworthy than any backtest right now.
- Why is VWAP_TREND going 5/14 (36% WR)?
- Why is TREND_UP regime 9/78 (11.5% WR)?
- Use BQ data to answer these directly — no backtest needed

### Option C: Reduce production complexity
- Disable all intraday setups (VWAP_TREND, VWAP_REVERSAL, OPEN_DRIVE, MORNING_FADE, PHASE1_MOMENTUM)
- Keep only swing (BREAKOUT, MOMENTUM, PULLBACK, MEAN_REVERSION) — the setups our backtest CAN model
- Live performance becomes interpretable; backtest becomes meaningful
- Trade fewer signals but with statistical confidence

### NOT recommended: Phase 10 testing more hypotheses
Until the replay is fixed and matches live, more backtests will just produce more wrong numbers.

## Section 7 — Honest Self-Assessment

I made these specific mistakes in the Phase 0-9 work:

1. **Phase 2 validator was checked-the-box, not rigorous.** I should have compared blocked_reason distributions, not just qualified count.

2. **I assumed importing the scoring code was sufficient.** Production has 4+ gates AFTER scoring. Importing one function doesn't import the gating pipeline.

3. **I scoped to SWING_SETUPS without verifying that's where production lives.** Live production is dominantly INTRADAY. We backtested a subset and reported on the whole.

4. **Each new finding became a new backtest target** instead of pausing to audit comprehensively. The user had to force this audit.

5. **I never compared backtest predictions to live trades.** A single BQ query would have shown the 9× volume discrepancy weeks ago.

This document is the honest reset. The right next steps depend on which option above
you want to pursue.
